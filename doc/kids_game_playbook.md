# 子ども向け学習ゲーム制作プレイブック

- 文書種別: 横展開用ノウハウ集 / 設計プレイブック
- 出典: 漢字読みRPG(taiyo-kanji-summer)の実装・実機検証で得た知見
- 対象: 小学生向け学習ゲーム全般(そろばん・計算・英語など)
- 使い方: 新規プロジェクト開始時にこのファイルをコピーし、企画・実装の基準にする

# 1. 一番大事な一行

> **子どもの意識を「ドリルを解いた」ではなく「ドラゴンを倒した」にする。**

学習行為そのものをゲームの操作にマッピングする。
「問題に正解するとゲームが進む」ではなく、**「学習行為 = 攻撃コマンド」**。

- 漢字RPG: 声で読む = 攻撃
- そろばんなら: 珠をはじいて答えを出す = 攻撃、が同型

# 2. 体験原則(全ゲーム共通)

## 2.1 機械のミスと子のミスを区別する

入力認識(音声・手書き・カメラ等)には必ず誤認識がある。
**誤認識を子どもが「自分が間違えた」と受け取ると、学習意欲が直接削れる。**

- 判定は boolean にしない。`CORRECT / AMBIGUOUS(機械が怪しい) / INCORRECT / NO_INPUT` の4値以上
- AMBIGUOUS はノーペナルティで「もういちど きかせて！」
- ❌マークは原則出さない(機械のミスか本人のミスか、システムには区別できないため)

## 2.2 進行不能禁止・必ず成功で終わる

どんなに分からなくても、最後は
「答えを見る → 復唱(再入力) → 攻撃が出る → 次へ」で必ず前へ進む。
**全問題が「できた」で終わる**(エラーレス学習)。ゲームオーバーは作らない。

## 2.3 罰を強くしない

- 誤答でコンボを切らない(初期版)。罰が強いと「入力しない」方向へ学習する
- 沈黙・タイムアウトを失敗扱いしない(考えるのが遅い ≠ 知らない)
- 敵からの反撃・HP減少などの「怖い罰」は入れない

## 2.4 1画面1主役

主役は常に「問題」(漢字・数式)。敵やエフェクトより視認性を優先。
問題表示は高解像度・最大級・余白広く。装飾で潰さない。

# 3. 子どもが喜ぶ要素(実証済みランキング)

実機で子どもに刺さった順。新ゲームでも優先的に入れる。

## 3.1 コレクション(最強)

**子どもはとにかくコレクションが好き。** 学習対象そのものを収集物にする。

- 漢字RPG: 習得した漢字102字が1枚ずつカードで埋まる図鑑
- そろばんなら: クリアした段位・攻略した数のモンスター等
- 「? のシルエットカード」で未取得を見せる(埋めたくなる)
- 進捗バッジ「34 / 102」をトップ画面に常時表示

## 3.2 レアカード+レアリティ

- R / SR / SSR の3段階。SSRは虹枠+ホロ(流れる光沢)で明確に「特別」
- 宝箱の排出率: R 70% / SR 24% / SSR 6%(SSRは平均17回に1枚 ≒ ちょうどいい執着)
- **初回ステージクリアはボスカード確定**(「ぬしを倒したらぬしのカード」の納得感)
- 同レアリティ内は未所持優先で抽選(コレクションが確実に進む)
- ダブりは ×2 表示(無駄になった感を出さない)

## 3.3 攻撃した感のエフェクト(小学生男子に特効)

「上品な演出」は刺さらない。以下をワンセットで:

- **画面全体の白フラッシュ**(0.16秒)
- **画面ごとシェイク**(通常0.3秒 / クリティカルは回転混じり0.45秒)
- **パーティカル飛散**(通常9個 / クリティカル16個 / 撃破22個)
- **ダメージ数字の叩きつけ**(3.2倍サイズから着地してバウンド、ピクセルフォント)
- 撃破時は爆発リング+金色パーティクル

ただし所要時間は 0.4〜0.9秒 厳守(§5参照)。派手さと短さは両立できる。

## 3.4 コンボ・クリティカル

- コンボ倍率: 1〜2連続 x1.0 / 3〜4 x1.15 / 5〜7 x1.3 / 8〜 x1.5
- クリティカルは**ランダムにしない**。「学習上うれしい行動」(連続正解・苦手克服・初見即答)を派手に報酬化する
- 数字はピクセルフォント・大きく・弾ませる

## 3.5 ボス・ワールド進行

- 1ステージ = 通常敵2〜3体+ボス、8〜12問、3〜5分(「あと1ステージ」が成立する長さ)
- 単元を露骨に見せない。「第2単元」ではなく「ささやきの森」
- ステージ選択カードにボスの顔を出す(次の目標が見える)

# 4. 入力状態のUX(認識系入力の要)

**「今なにをすべきか」を子どもが迷った瞬間、連打・連呼が始まる。**
(実例: マイクの待ち状態が分からず、子どもが答えを連呼した)

## 4.1 2値カラールール

状態表示は「色2値」まで単純化する:

- **みどり = いま入力していい**(バナー脈動+問題カード自体がみどりに発光)
- **それ以外(黄/グレー)= まってて**

「はんてい中」「じゅんび中」などの中間状態は、子どもには全部「まってて」。

## 4.2 入力が届いた瞬間の即時フィードバック(連打防止の核心)

認識結果の確定を待たずに、**入力が届いた瞬間**に「きこえてるよ…！」+音量バー表示。
これが無いと子どもは「届いてない」と判断して連呼・連打する。
そろばん・手書きでも同じ: ストローク・タップが届いた瞬間に必ず反応を返す。

## 4.3 音の合図(BGMダッキング)

入力受付中はBGMを**約45%まで220msフェード**で下げる。
「BGMがスッと引く = きみの番」という聴覚合図になる。
(仕様書的な70〜85%では合図として聞こえない。深めに)

# 5. 演出の時間規律

> 演出を見る時間 > 学習する時間 になったら本末転倒。

| 演出 | 長さ |
|---|---|
| 問題表示 | 0.2〜0.4秒 |
| 通常攻撃 | 0.4〜0.7秒 |
| クリティカル | 0.6〜0.9秒 |
| 敵撃破 | 0.5〜0.95秒 |
| 必殺技(あれば) | 1.0〜1.5秒 |
| クリアジングル | 2〜8秒 |

発話(入力)時間を除いて「1〜1.5秒で次の問題」のテンポを守る。

# 6. ヒント設計(わからない時の救済)

## 6.1 実証済みの構成

- **子どもが自分で助けを呼ぶ**(声のゲームなら「ヒント！」と叫ぶ=呪文感覚。タップゲームならヒントボタン)
- 1回目: マスクヒント(「ひ○う」方式: 最初と最後だけ見せる)
- 2回目: 答え表示+「いっしょに言ってみよう」→ 復唱で必ず攻撃が出る
- **自動ヒントは入れない**(考える時間は子どもによって違う。沈黙は「よんでみよう！」の促しだけ)

## 6.2 ヒント連打対策は「禁止」ではなく「経済」で

- ヒント使用後の正解: **ダメージ×0.5・コンボ増えない・クリティカル無効**
- **減っていることを視覚化する**: 数字が小さく青灰色+「ヒントで はんぶん ▼」、フラッシュ/シェイクも無し
- 「知ってると強い」が体感できれば、子どもは自然にノーヒントを狙う
- 将来: ヒントを使った問題を後日再出題 → ノーヒント正解で「WEAK POINT!」特大ボーナス(回収ループ)

# 7. アーキテクチャ(そのまま流用可)

## 7.1 レイヤー分離

```text
src/
├── app/              … 起動・シーン遷移・依存の組み立て
├── domain/           … 画面を一切知らないゲーム/学習ロジック
│   ├── battle/       … Engine(入力評価→イベント列)、コンボ、ダメージ
│   ├── learning/     … 問題データ、正規化、判定、出題選択
│   └── progression/  … 進行度、統計
├── application/      … Controller(状態機械)とRenderer契約(interface)
├── infrastructure/   … 入力API(音声等)、保存、オーディオ
├── presentation/     … シーン(DOM)。学習内容を一切判断しない
└── data/             … 問題・敵・ステージ・カード(全部データ駆動)
```

鉄則:

- **Engine は `submit(評価結果)` → `イベント列` を返すだけ**。Presentation はイベントを順に再生する。ロジック側に `playAnimation()` を書かない
- 入力は interface で抽象化(`SpeechRecognizer` → そろばんなら `AbacusInput` 等)。差し替えてもゲーム本体は不変
- 敵データと学習データを分離(問題に enemy を書かない。ステージが enemyId と questionPoolId を結ぶ)
- ゲームエンジン(Phaser等)は**不要**。DOM+CSSアニメで十分に派手にできる。TypeScript+Vite素朴構成が最速

## 7.2 検証をスクリプトで機械化する

- 出題の偏りは**実装そのものを使うシミュレータ**で1000件回して統計検証(カイ二乗)
- 教材カバレッジ(全102字が問題に含まれるか等)はチェックスクリプトで機械検証
- 「目視で確認した」は信用しない。`npx tsx scripts/check-*.ts` を用意する

# 8. 永続化(「アップデートで消えた」と言わせない)

子どものデータが消えると本気で泣かれる。以下を必ず:

- localStorage のキーは固定(キー名にバージョンを入れない)。データ内に `schemaVersion`
- 旧形式は migration 関数チェーンで読み替え
- **書き込みは常に追加型マージ**(取得日時は古い方・回数は多い方)。減る方向の操作は `reset()` 以外コード上に存在させない
- パース不能な壊れデータも消さず `-backup-<ts>` キーへ退避してから初期化
- 運用側からの初期付与用に `SYSTEM_GRANTS`(起動ごとに冪等適用)を用意
- `?debug=1` でコンソール管理API(`grantAll / reset / exportJson / importJson`)
- 子ども側にもJSONエクスポートボタン(機種変更の引き継ぎ)

# 9. サウンド設計

## 9.1 役割分担

- **BGM = 世界観とワクワク**。少数精鋭6曲で開始できる: タイトル / 通常×ワールド数 / ボス / クリアジングル / ごほうびジングル
- **SE = 手応えと状態通知**。外部素材でなく**Web Audioコード生成**(容量ゼロ・即応・調整自在)。コアSE 10種で足りる

## 9.2 音声認識・録音と併用するゲームの鉄則

- BGMは**インスト必須**(歌声はSTTが歌詞を拾う)
- 入力受付中はBGMダッキング(§4.3)
- 失敗音はブザー禁止。「ポン」程度の軽い下降音

## 9.3 iOSの罠: 音量ボタンが効かない

マイク使用中のiOSはWeb Audio出力が「録音+再生」セッションになり、
**ハードウェア音量ボタンで調整できない(大きめ固定)**。

→ **アプリ内の音量設定画面(SE/BGM別スライダー+localStorage保存)は必須装備。**
スライダーを動かすたびにサンプル音を鳴らして耳で確認できるようにする。

# 10. AI画像アセット量産(コスト制御込み)

## 10.1 パイプラインの型

1. **スタイル固定文**を全プロンプトに必ず入れる(Modern Pixel Fantasy / 対象年齢 / not scary / readable silhouette / consistent look)
2. カテゴリ別バッチで生成(敵・背景・UI・エフェクトを混ぜない)
3. 命名規則 `category__theme__name__vNN.png` で concepts → 採用を final へ昇格 → 以後の基準画像
4. 当たり画像のルックに寄せて量産

## 10.2 透過アセットの現実解

- gpt-image-2 は `background: transparent` 非対応(市松模様を絵として描き込む)
- → **マゼンタ(#FF00FF)単色背景で生成し、ローカルでクロマキー抜き**(強マゼンタのみキー、エッジをフェザリング+デスピル。キャラの紫・ピンクは保護)

## 10.3 コスト制御の型(重要)

- **文字は画像に焼かない**(漢字・数字・UIテキストは必ずコード描画)
- カード背景は**10種だけ生成**し、割当・枠色相・光沢角は文字列ハッシュで決定論的に変化 → 10枚の費用で102枚が全部違って見える
- キャラ絵は使い回す: バトル敵 = そのままレアカード絵(追加費用ゼロ)。コレクション専用は本当に欲しい分だけ追加
- 背景(不透過)はJPEG化で1枚150KB程度に

# 11. 出題・難度設計

- 問題プールは単元ごと(1ステージ1単元)。プールサイズ ≧ ステージ最大出題数+1(ステージ内重複防止)
- シャッフルデッキ方式+周回またぎの連続ガード(完全ランダムは体感が偏る)
- 音訓・表記ゆれなど**正解のバリエーションを accepted リストで持つ**(入力認識の表記ゆれを救う)
- 認識装置が間違えやすい候補は accepted と**別リスト**(sttConfusions相当)で持ち、正解にせずノーペナルティ再試行にする。実機ログから育てる
- 未習内容が混ざらないよう出題語を検査する(上級学年の字が入った語は差し替え)

# 12. ホスティング・配布

- **GitHub Pages で十分**(無料・HTTPS標準=マイク等が動く・push自動デプロイ)
- Vite は `base` をCI環境変数で切替。**コード内のアセットパスは必ず `assetUrl()` ヘルパー経由**(サブパス配信対応)。CSSは相対参照
- APIキーは `.env`(gitignore)+ 公開前に `git log --all -- .env` で履歴混入ゼロを確認
- ローカル実機テストは自己署名SSL(`@vitejs/plugin-basic-ssl`)+LAN IP

# 13. iOS/ブラウザの罠チェックリスト

実際に踏んだものだけ。新プロジェクトで最初に読み返す。

1. **自動再生制限**: 初回ロードでBGMは絶対鳴らない。「最初のタップ(どこでも)で解錠して鳴らす」を実装。play()失敗時に再生中フラグを残さない(実態は `el.paused` で判定)
2. **オーディオ解錠のプライミングは同期で**: ジェスチャー内で `play(); pause();` を同期実行。promiseの後始末で pause すると本再生とレースして多重再生や無音になる
3. **マイク使用中は音量ボタンが効かない** → アプリ内音量設定(§9.3)
4. **PWA(ホーム画面追加)でSpeechRecognitionが動かない場合がある**(WebKitバグ)→ Safariタブ運用を第一候補に、PWAは別途検証
5. マイク・カメラは secure context 必須(https or localhost)
6. 縦持ち・safe-area・`100dvh`。スクロールが必要な画面は `justify-content: center` + overflow で上端が切れる(flex-start+auto scrollへ)
7. Chrome拡張やツールでの自動テストは localhost 権限で詰まりがち。実機確認の導線(QR等)を最初から用意

# 14. 進め方の型(プロセス)

1. **PoC仕様書を先に書く**: 「技術が動くか」ではなく「採用判断の質問リスト(YES/NO)」と合格基準(数値)を先に決める
2. 入力認識の実用性を最小実装で検証(ゲーム性は最低限)→ 判断 → 本実装
3. 本実装はレイヤー分離(§7)で開始。PoCコードは新構造に吸収
4. アセットは Phase 1(方向性確認の少数生成)→ 当たり決定 → 量産
5. 計測ログ(入力ごとの生データ・正誤・遅延・リトライ)は最初から仕込む。改善は全部ログ駆動
6. 実機で子どもに遊ばせて、口から出た不満をそのまま次のタスクにする
   (実例: 「聞こえてないのかな」→ 即時フィードバック実装 / 「音がでかい」→ 設定画面)

# 15. そろばんゲームへの当てはめ(参考)

同じ骨格で作れる想定:

```text
入力Adapter: SpeechInput → AbacusInput(画面上の珠 or 実物+カメラ or 数字読み上げ)
Challenge:   ReadingChallenge → CalcChallenge(出題: 「27 + 15」/ 期待値: 42)
判定4値:     CORRECT / AMBIGUOUS(入力途中・読み取り不明) / INCORRECT / NO_INPUT
攻撃:        答えが合う = 攻撃。暗算の速さでクリティカル(学習上うれしい行動の報酬化)
コレクション: 数字カード? 段位バッジ? 計算モンスター図鑑?
ヒント:      「ヒント！」→ 途中式 or 珠の置き方を1手だけ見せる → ダメージ半減
```

BattleEngine・コンボ・宝箱・コレクション・保存・設定・エフェクトは
ほぼコピーで動く。作り直すのは learning ドメインと入力Adapterだけ。

# 16. やってはいけないこと(総集編)

- 毎問「ボタンを押してください」
- 誤認識で「不正解！❌」
- 長い攻撃ムービーを毎問見せる
- 苦手問題だけ延々出す
- ゲームUIの中に学習ロジックを直接書く
- 認識装置の間違い候補を無条件で正解にする
- レベル不足で学習ステージをロックする
- 子どものデータが減る方向の書き込みを作る
- 文字・数字を画像に焼き込む
- ふりがな(答え)常時表示
- 沈黙や誤答への「怖い罰」
